## Shared Knowledge

All models use multi-tenant client_id scoping. The PocketExpenseService handles FX conversion via PocketExpenseFXService for all expense operations. CSV validation uses PocketExpenseCSVValidator with preloaded reference data. Background processing via ProcessExpenseUpload job handles batch CSV imports. All API responses use API Resources for consistent formatting. Form Requests handle validation with policy authorization. Soft delete patterns use both flag-based (deleted/delete_time) and Laravel SoftDeletes (deleted_at) depending on table conventions.

## Anything UNCLEAR

Several implementation details need clarification: 1) The notification channel for batch upload completion - whether to use in-app notifications, email, push notifications, or a combination, as the platform notification infrastructure existence is marked as UNKNOWN. 2) The exact integration pattern for FX conversion - whether this reuses an existing platform FX service or requires new integration, and the specific API endpoints for the wallet-ccy-value service and FX rate lookup. 3) The audit logging implementation approach for permission grants/revokes - whether to use a separate audit table, event sourcing, or Laravel activity log package. 4) The ClientFeatures model query pattern to check if client_id has feature_id=16 enabled, as the backing table structure is not defined. 5) Whether to use flag-based soft delete (deleted + delete_time) or Laravel SoftDeletes (deleted_at) for new tables, as both patterns coexist in the platform. These decisions should be made before implementation to ensure consistency with existing platform patterns.
