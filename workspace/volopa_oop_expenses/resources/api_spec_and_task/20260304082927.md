## Shared Knowledge

All models use the existing Volopa authentication middleware (OAuth2) for API security. The system leverages existing platform infrastructure including FX services, file storage, and notification systems. Database tables follow Laravel naming conventions with snake_case table names mapping to PascalCase model names. All new tables include client_id for multi-tenant data isolation. The soft delete pattern uses either Laravel's SoftDeletes trait (deleted_at) or flag-based approach (deleted + delete_time) depending on table design. CSV processing uses Laravel queues for background job handling with batch processing of 100 records. FX conversion integrates with existing platform services but implements project-specific commission calculation and 30-day lookback logic. All API responses use Resource classes to shape output and hide internal model structure.

## Anything UNCLEAR

Three architectural decisions need clarification: (1) Notification delivery mechanism for batch upload completion - whether to implement in-app notifications, email notifications, or both depends on existing platform notification infrastructure capabilities. (2) Table naming convention inconsistency between singular ('client', 'user') and plural ('clients', 'users') references in foreign key definitions requires confirmation of actual platform convention. (3) FX conversion service integration pattern - while the platform has FX services, the specific implementation approach for expense-specific features like commission calculation and 30-day lookback needs architectural guidance on code reuse vs new service development.
