## Implementation approach

We will build a Laravel 10+ API system for Volopa OOP Expenses using a multi-module approach: (1) User Management with permission delegation via user_feature_permission table supporting hierarchical RBAC, (2) CSV Batch Upload with synchronous validation and asynchronous processing using Laravel queues, (3) Single Expense CRUD with real-time FX conversion. The system leverages existing Volopa infrastructure including OAuth2 middleware, multi-tenant architecture, and master data tables. Key technical decisions include using Laravel's native validation via FormRequests, API Resources for response shaping, Eloquent models with explicit relationships, and queue jobs for background processing. The architecture follows Laravel best practices with thin controllers, service layer for business logic, and proper separation of concerns. We'll implement atomic validation for CSV uploads, flexible metadata storage via pivot tables, and integrate with existing FX infrastructure for currency conversion.

## System constraints

- Maximum 200 rows per CSV file upload
- CSV file format must be CSV or TXT with CSV content, maximum 10MB (10240 KB)
- CSV header row is mandatory and must exactly match required column names
- All-or-nothing validation: if any CSV row fails validation, no expenses are created
- Date format must be DD/MM/YYYY and not older than 3 years from current date
- Currency code must be 3-letter ISO format and exist in platform supported currencies list
- Amount sign is determined by expense type: Refund = positive, others = negative
- VAT percentage must be numeric between 0-100 with % sign stripped during validation
- Merchant name maximum length is VARCHAR(180) as per database definition
- Maximum 20 active expense sources per client with unique names per client
- Three default expense sources auto-created on feature enable: Cash, Corporate Card, Personal Card
- Global 'Other' expense source (client_id = NULL) cannot be deleted or edited
- FX rate lookup has maximum 30-day lookback from expense date, return 'No FX Available' if not found
- FX commission formula: AdjustedRate = BaseRate x (1 - Comm%)
- Backend must recalculate FX conversion on save, do not trust frontend-only values
- All API routes must use Oauth2UserClient middleware for authentication
- All queries and mutations must be scoped by client_id for multi-tenancy
- user_id must match authenticated user with server-side verification
- Target entities (expense_user_id) must belong to the same client_id as requester
- Only Primary Admin has full access to all users by default
- Admin gets full access only to own expenses by default, needs explicit grant for others
- Business User and Card User cannot approve expenses even with management rights
- Admin can only grant access to their own managed users, not all users
- All new tables must use InnoDB engine with utf8mb4 charset and utf8mb4_unicode_ci collation
- pocket_expense_source_client_config uses flag-based soft delete (deleted + delete_time)
- pocket_expense uses flag-based soft delete (deleted + delete_time)
- pocket_expense_metadata uses flag-based soft delete (deleted + delete_time)
- pocket_expense_file_uploads uses Laravel SoftDeletes (deleted_at)
- pocket_expense uses Volopa legacy timestamps (create_time, update_time)
- pocket_expense_file_uploads uses Laravel standard timestamps (created_at, updated_at)
- user_feature_permission uses Laravel standard timestamps (created_at, updated_at)
- opt_pocket_expense_type must be seeded with: ATM Withdrawal (negative), Point of Sale (negative), Fee & Charges (negative), Refund from Merchant (positive)
- Create ONE Migration and ONE Factory per new table defined in database schema
- Create ONE Eloquent Model per new table using PascalCase naming convention
- Create ONE Policy per module that needs authorization (PocketExpensePolicy, UserFeaturePermissionPolicy)
- Create ONE FormRequest per API endpoint for validation and authorization
- Create ONE Service per domain operation (CRUD, validation, conversion, permission management)
- Create ONE API Resource per model returned in responses to hide internal fields
- Create ONE Controller per API resource group with thin controllers delegating to services
- Use transactions when touching multiple tables in single operation
- Return proper HTTP status codes: 200 (OK), 201 (Created), 204 (No Content), 400 (Bad Request), 401 (Unauthorized), 403 (Forbidden), 404 (Not Found), 422 (Unprocessable Entity)
- Do not return raw Eloquent models in API responses, use API Resources
- Do not use session/redirect patterns in APIs, maintain stateless design
- Do not expose stack traces or sensitive error details in production
- Do not disable mass-assignment protection or trust client-owned fields
- Do not create N+1 queries, especially in API Resources - use eager loading
- Do not return unbounded lists, implement pagination using Resource::collection($query->paginate())
- Do not forget transactions for multi-write operations
- Expense status enum values: draft, submitted, approved, rejected
- Upload status enum values: uploaded, validation_failed, validation_passed, processing, completed, failed, sync_failed
- Metadata type enum values: category, tracking_code_type_1, tracking_code_type_2, project, additional_field, file, expense_source
- Amount sign enum values: positive, negative
- Staging data status enum values: pending, processing, synced, failed

## Anything UNCLEAR

Several implementation details require clarification: (1) The specific notification channel for batch upload completion (in-app, email, or push notifications) - this affects the ProcessExpenseUpload job implementation. (2) Whether the FX conversion reuses existing platform FX service infrastructure or requires new integration - the /wallet-ccy-value endpoint is mentioned but the full FX service contract is unclear. (3) The exact audit logging mechanism for permission grant/revoke operations - whether to use Laravel activity log, event sourcing, or dedicated audit table. (4) The ClientFeatures model query pattern to check if client has OOP feature enabled (feature_id = 16) - the backing table structure is not defined. (5) Table naming conventions as specs reference both singular ('client', 'user') and plural ('clients', 'users') forms. (6) The exact soft delete pattern preference since both flag-based (deleted + delete_time) and Laravel SoftDeletes (deleted_at) patterns appear in different tables. These decisions may require input from the platform architecture team or existing codebase review to ensure consistency with existing Volopa infrastructure.
