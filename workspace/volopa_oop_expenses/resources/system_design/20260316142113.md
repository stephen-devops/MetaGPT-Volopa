## Implementation approach

We will build a comprehensive Laravel 10+ API system for Volopa's Out-of-Pocket Expenses with three core modules: (1) User Management & Permissions using a delegation-based RBAC system with user_feature_permission table, (2) CSV Batch Upload with synchronous validation and asynchronous processing via Laravel queues, and (3) Single Expense CRUD with real-time FX conversion. The architecture follows Laravel best practices with thin controllers, service classes for business logic, Form Requests for validation, API Resources for response shaping, and Eloquent models with proper relationships. We'll use existing Volopa infrastructure including OAuth2 middleware, FX services, and multi-tenant client scoping. The system implements atomic operations for CSV processing (all-or-nothing validation), background job processing for bulk uploads, and flexible metadata storage through a normalized schema. Key technical components include: normalized database schema with proper foreign keys and soft delete patterns, comprehensive validation service for CSV processing, FX conversion service with client commission calculation, permission policy enforcement, and audit trail capabilities.

## System constraints

- Maximum 200 rows per CSV file upload
- All-or-nothing validation: if any CSV row fails validation, no expenses are created
- FX rate lookup limited to maximum 30-day lookback from expense date
- Merchant Name maximum length 180 characters (VARCHAR limit)
- Notes field must be trimmed and prevent SQL injection
- Only Primary Administrator has full access to all users by default
- All queries and mutations must be scoped by client_id for multi-tenancy
- user_id must match authenticated user (server-side validation)
- Target entities (expense_user_id) must belong to the same client_id
- Routes must be added to routes/api.php under /v1 prefix with auth middleware
- Controllers must be thin and delegate business logic to services
- Use transactions when touching multiple database tables
- Return proper HTTP status codes: 200 (OK), 201 (Created), 204 (No Content), 400 (Bad Request), 401 (Unauthorized), 403 (Forbidden), 404 (Not Found), 422 (Unprocessable Entity)
- Create API Resources to shape responses and hide internal model fields
- Use Form Requests for validation with Policy authorization
- Add pagination using Resource::collection($query->paginate())
- New tables must use InnoDB engine with utf8mb4 character set and utf8mb4_unicode_ci collation
- All new tables must include client_id as NOT NULL or foreign key constraint
- Follow soft delete pattern: deleted TINYINT(1) DEFAULT 0 and delete_time DATETIME DEFAULT NULL
- Use Volopa timestamp pattern: create_time DATETIME DEFAULT CURRENT_TIMESTAMP and update_time DATETIME DEFAULT NULL ON UPDATE CURRENT_TIMESTAMP
- Create ONE Migration per new table with proper foreign key constraints
- Create ONE Eloquent Model per table with defined relationships
- Create ONE Policy per module requiring authorization
- Create ONE Service per domain operation (CRUD, validation, FX conversion)
- Maximum 20 active expense sources per client
- Unique constraint on (client_id, name) for expense sources
- Date format validation: DD/MM/YYYY for CSV input
- Currency Code must be 3-letter ISO format from approved list
- VAT percentage must be numeric between 0-100 (strip % sign)
- Amount sign determined by expense type (Refund=positive, others=negative)
- Source Note required when Source equals 'Other'
- Expense date must not be older than 3 years
- File upload constraints: CSV or TXT format, maximum 10MB size
- Header row mandatory with exact column name matching
- Commission formula: AdjustedRate = BaseRate x (1 - Commission%)
- Backend must recalculate FX on save (do not trust frontend values)
- Use Laravel SoftDeletes trait for pocket_expense_file_uploads table
- Use flag-based soft delete (deleted + delete_time) for pocket_expense and related tables
- Queue job processing in batches of 100 records for performance
- Business Users and Card Users cannot approve expenses even with management rights
- Admin role can only grant access to their own managed users, not all users
- Managing access can be assigned to any user regardless of role
- Expense status enum values: 'draft', 'submitted', 'approved', 'rejected'
- Upload status enum values: 'uploaded', 'validation_failed', 'validation_passed', 'processing', 'completed', 'failed', 'sync_failed'
- Metadata type enum values: 'category', 'tracking_code_type_1', 'tracking_code_type_2', 'project', 'additional_field', 'file', 'expense_source'
- Unique constraint on (pocket_expense_id, metadata_type, deleted) in pocket_expense_metadata
- Unique constraint on (user_id, client_id, feature_id) in user_feature_permission
- Don't return raw Eloquent models in API responses
- Don't use session/redirect patterns in APIs
- Don't return 200 status for error conditions
- Don't create N+1 queries especially in API Resources
- Don't forget database transactions for multi-write operations
- Don't expose stack traces or sensitive error details in API responses
- Don't disable mass-assignment protection or trust client-owned fields
- Don't build query filters directly from user input without validation

## Anything UNCLEAR

Three areas need clarification: (1) The specific notification mechanism for batch upload completion - should we implement in-app notifications, email notifications, or both? The specs reference notification but don't specify the channel. (2) The FX conversion integration pattern - while we know there's an existing /wallet-ccy-value endpoint and FX infrastructure, the exact API contract for retrieving historical FX rates with client-specific commissions needs to be defined. (3) The audit logging implementation - should we use Laravel's built-in activity log package, implement a custom audit table, or use an event sourcing pattern for tracking permission grants/revokes and expense modifications? These decisions will impact the final implementation approach but don't block the core system architecture.
