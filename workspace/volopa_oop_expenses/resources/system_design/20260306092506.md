## Implementation approach

We will build a comprehensive Laravel 10+ API system for OOP (Out-of-Pocket) Expenses with three interconnected modules. The implementation follows Laravel best practices with a mental model of: Client -> versioned routes with auth middleware -> thin controllers -> Form Request validation with policies -> domain services -> API Resources for response shaping. We'll use Eloquent ORM with explicit relationships, Laravel's built-in validation and policy systems, queue jobs for background processing, and API Resources to hide internal fields. The architecture emphasizes multi-tenancy (all operations scoped by client_id), role-based delegation through user_feature_permission table, atomic validation for CSV uploads, real-time FX conversion with user override capability, and comprehensive soft delete patterns. We'll leverage existing Volopa infrastructure including OAuth2 middleware, FX services, file storage, and queue system while maintaining backwards compatibility.

## System constraints

- Maximum 200 rows per CSV file upload
- All-or-nothing validation: if any CSV row fails validation, no expenses are created
- FX rate lookup maximum 30-day lookback from expense date
- Merchant Name maximum length VARCHAR(180) per database definition
- Only Primary Administrator has full access to all users by default
- All queries and mutations must be scoped by client_id for multi-tenancy
- user_id must match authenticated user with server-side verification
- Target entities (expense_user_id) must belong to the same client_id
- Routes must be added to routes/api.php under authentication middleware
- Controllers must be thin and delegate business logic to services
- Use transactions when touching multiple database tables
- Return proper HTTP status codes (200, 201, 204, 400, 401, 403, 404, 422)
- Create API Resources to shape responses and hide internal fields
- Use Form Request classes for validation with policy enforcement
- Date format for CSV must be DD/MM/YYYY, not older than 3 years
- Currency Code must be 3-letter ISO and in platform allowed list
- Amount sign determined by expense type (Refund = positive, others = negative)
- VAT percentage must be numeric between 0-100, strip % sign
- Source must match configured sources for client including global Other
- Source Note required when Source = Other
- Maximum 20 active expense sources per client
- Unique source names per client (client_id, name constraint)
- InnoDB engine required for all new tables
- Character set utf8mb4 with utf8mb4_unicode_ci collation
- Soft delete using deleted TINYINT(1) and delete_time DATETIME pattern
- Timestamp pattern using create_time/update_time DATETIME columns
- Do not return raw Eloquent models from API endpoints
- Do not use session/redirect patterns in APIs
- Do not return 200 status codes for error conditions
- Do not expose stack traces or sensitive error details
- Do not disable mass-assignment protection
- Do not build query filters directly from user input
- Do not create N+1 queries, especially in API Resources
- Do not return unbounded lists without pagination
- Do not forget transactions for multi-write operations
- Backend must recalculate FX rates on save, do not trust frontend values
- Commission formula: AdjustedRate = BaseRate × (1 - Commission%)
- CSV file maximum size 10MB (10240 KB)
- CSV header row mandatory with exact column name matching
- File format must be CSV or TXT with CSV content
- Notes field must be trimmed and prevent SQL injection
- Global 'Other' expense source (client_id = NULL) not deletable or editable
- Three default sources auto-created on feature enable: Cash, Corporate Card, Personal Card
- Expense status enum values: draft, submitted, approved, rejected
- Expense type amount_sign enum values: positive, negative
- Permission is_enabled boolean defaults to true
- All new migrations must follow Laravel naming conventions
- Models must define explicit relationships with proper foreign key constraints
