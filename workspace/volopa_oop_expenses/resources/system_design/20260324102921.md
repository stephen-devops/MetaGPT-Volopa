## Implementation approach

We will build a Laravel 10+ API system with three core modules: 1) User Management & Permissions using a delegation table (user_feature_permission) with role-based hierarchy, 2) CSV Batch Upload with synchronous validation and async processing via Laravel queues, and 3) Single Expense CRUD with real-time FX conversion. The system leverages existing Volopa infrastructure including OAuth2 middleware, multi-tenant scoping, and platform services for FX rates. We'll use Laravel's built-in features: Eloquent ORM for data modeling, Form Requests for validation, API Resources for response formatting, Policies for authorization, Jobs for background processing, and Factories for testing. The architecture follows thin controllers with business logic in dedicated services, ensuring separation of concerns and maintainability.

    DB-->>FX: Base currency info
    FX-->>PEC: Currency data
    PEC->>FX: getFXRate(fromCurrency, toCurrency, date)
    FX-->>PEC: FX rate with commission
    PEC->>PES: createExpense(expenseData, userId, clientId)
    PES->>DB: Begin transaction
    PES->>DB: Insert pocket_expense
    PES->>DB: Insert pocket_expense_metadata records
    PES->>DB: Commit transaction
    DB-->>PES: Expense created
    PES-->>PEC: PocketExpense model
    PEC-->>Client: 201 Created with PocketExpenseResource
    
    Note over Client, DB: CSV Batch Upload Processing Flow
    Client->>Auth: POST /api/uploads/pocket-expense/csv
    Auth->>PUC: Multipart file upload request
    PUC->>PUC: Basic file validation (size, type, permissions)
    PUC->>DB: Create PocketExpenseFileUpload record (status=uploaded)
    PUC->>CSV: validate(filePath, targetUserId, clientId, adminId)
    CSV->>CSV: preloadReferenceData(clientId)
    CSV->>CSV: validateHeaders(headers)
    CSV->>CSV: Loop validateRow() for each data row
    CSV-->>PUC: Validation result (errors or valid rows)
    PUC->>DB: Update upload record with validation results
    alt Validation Failed
        PUC-->>Client: 422 Unprocessable Entity with error details
    else Validation Passed
        PUC->>DB: Bulk insert to pocket_expense_uploads_data (status=pending)
        PUC->>Queue: Dispatch ProcessExpenseUpload job
        PUC-->>Client: 200 Success with upload_id
        Queue->>Job: Execute ProcessExpenseUpload
        Job->>DB: Query pending upload data in batches
        Job->>PES: Bulk sync expenses to main service
        Job->>DB: Update upload status to completed
    end

## System constraints

- All API routes must use Oauth2UserClient middleware for authentication
- All queries and mutations must be scoped by client_id for multi-tenancy
- Maximum 200 rows per CSV file upload with 10MB file size limit
- CSV file format must be CSV or TXT with mandatory header row matching exact column names
- All-or-nothing validation: if any CSV row fails, no expenses are created
- Date format in CSV must be DD/MM/YYYY and not older than 3 years
- Currency codes must be 3-letter ISO format and validated against platform currency list
- Amount sign determined by expense type: Refund = positive, others = negative
- VAT percentage must be numeric between 0-100 with % sign stripped
- Merchant name maximum length is VARCHAR(180) per database definition
- FX rate lookup has maximum 30-day lookback from expense date
- FX conversion formula: AdjustedRate = BaseRate x (1 - Commission%)
- Backend must recalculate FX on save, do not trust frontend-only values
- 2-second debounce before triggering FX API calls for user input
- expense_user_id must belong to same client_id as requesting user
- user_id must match authenticated user via server-side validation
- Maximum 20 active expense sources per client with unique names
- Global 'Other' expense source (client_id = NULL) cannot be deleted or edited
- Three default expense sources auto-created: Cash, Corporate Card, Personal Card
- Source Note required when Source = Other is selected
- Expense status enum values: draft, submitted, approved, rejected
- Primary Admin has full access to all users by default
- Admin gets full access only to own expenses by default unless granted
- Business User and Card User cannot approve expenses even with management rights
- Only Primary Admin or Volopa Admin can revoke management rights
- Database engine must be InnoDB with utf8mb4 character set and utf8mb4_unicode_ci collation
- Use flag-based soft delete pattern: deleted TINYINT(1) and delete_time DATETIME
- Use Volopa legacy timestamp pattern: create_time and update_time DATETIME columns
- OptPocketExpenseType must seed with: ATM Withdrawal (negative), Point of Sale (negative), Fee & Charges (negative), Refund from Merchant (positive)
- Controllers must be thin and delegate business logic to services
- Use transactions for multi-table write operations
- Return proper HTTP status codes: 200 (OK), 201 (Created), 204 (No Content), 400 (Bad Request), 401 (Unauthorized), 403 (Forbidden), 404 (Not Found), 422 (Unprocessable Entity)
- API Resources must shape responses and hide internal model fields
- Form Requests must handle validation and authorization via policies
- Background jobs must process CSV uploads in batches of 100 records
- File uploads must be stored in storage/app/pocket-expense-uploads directory
- Queue job must update upload status: uploaded -> processing -> completed/failed
- Metadata types enum: category, tracking_code_type_1, tracking_code_type_2, project, additional_field, file, expense_source
- Unique constraint on pocket_expense_metadata: (pocket_expense_id, metadata_type, deleted)
- Foreign key constraints must reference existing platform tables: users(id), clients(id), transaction_category(id), tracking_codes(id), configurable_projects(id), file_store(id), expense_additional_field(id)
- Do not create OopExpense model or related artifacts - superseded by PocketExpense implementation
- Create ONE Migration and ONE Factory per new database table
- Each new table must have corresponding Eloquent Model with proper relationships defined
- Amount fields must use DECIMAL(14,2) data type for precision
- UUID fields must be VARCHAR(36) with nullable constraint
- All monetary calculations must preserve decimal precision
- CSV validation errors must include line_number, field, error description, and provided value
- ProcessExpenseUpload job must run on 'expense-processing' queue
- Notification must be sent to target user when batch upload completes
- Expense approval workflow must track approved_by_user_id and approval timestamps
