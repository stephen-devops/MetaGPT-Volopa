## Implementation approach

We will build a comprehensive Laravel 10+ API system for OOP Expenses with three core modules: (1) User Permission Management using a delegation-based RBAC system via user_feature_permission table, (2) CSV Batch Upload with synchronous validation and asynchronous background processing using Laravel queues, and (3) Single Expense CRUD with real-time FX conversion integration. The architecture follows Laravel best practices with thin controllers, service-layer business logic, Form Request validation, API Resources for response shaping, and Eloquent models with proper relationships. We'll use existing Volopa infrastructure (OAuth2 middleware, FX services, notification system) while implementing new components for expense-specific logic. The system ensures multi-tenant data isolation, atomic operations for batch processing, and flexible metadata storage through a normalized design. All endpoints follow REST conventions with proper HTTP status codes and structured error responses.

    ExpSvc->>DB: Insert pocket_expense_metadata
    DB-->>ExpSvc: Metadata attached
    ExpSvc-->>ExpCtrl: Complete expense with metadata
    ExpCtrl-->>Client: 201 {success: true, data: expense}
    
    Note over Client,DB: CSV Batch Upload Flow
    Client->>Auth: POST /api/uploads/pocket-expense/csv
    Auth->>UploadCtrl: Authenticated request with CSV file
    UploadCtrl->>UploadCtrl: Basic validation (file size, type, permissions)
    UploadCtrl->>DB: Create pocket_expense_file_uploads record (status=uploaded)
    DB-->>UploadCtrl: Upload record created
    UploadCtrl->>CSVValidator: validateCSV(filePath, targetUserId, clientId, adminId)
    CSVValidator->>CSVValidator: preloadReferenceData(clientId)
    CSVValidator->>DB: Load expense types, currencies, sources
    DB-->>CSVValidator: Reference data loaded
    CSVValidator->>CSVValidator: validateHeaders(headers)
    CSVValidator->>CSVValidator: validateRow(row, lineNumber) for each row
    CSVValidator-->>UploadCtrl: Validation result (errors or valid rows)
    
    alt Validation Failed
        UploadCtrl->>DB: Update upload record (status=validation_failed, errors)
        DB-->>UploadCtrl: Updated
        UploadCtrl-->>Client: 422 {success: false, errors: validationErrors}
    else Validation Passed

        DB-->>UploadCtrl: Staging data inserted
        UploadCtrl->>DB: Update upload record (status=processing)

        UploadCtrl->>Queue: dispatch ProcessExpenseUpload(uploadId)
        Queue-->>UploadCtrl: Job queued
        UploadCtrl-->>Client: 200 {success: true, upload_id, total_rows}
        
        Note over Queue,DB: Background Processing
        Queue->>ProcessJob: Execute job with uploadId
        ProcessJob->>DB: Fetch pending expense data in batches of 100
        DB-->>ProcessJob: Batch of expense records
        ProcessJob->>ProcessJob: syncExpensesBatch(expenseData)
        ProcessJob->>DB: Insert pocket_expense records
        DB-->>ProcessJob: Expenses created
        ProcessJob->>DB: Update uploads_data status to 'synced'
        DB-->>ProcessJob: Status updated
        ProcessJob->>ProcessJob: Repeat for all batches
        ProcessJob->>DB: Update upload record (status=completed, processed_at)
        DB-->>ProcessJob: Upload completed
        ProcessJob->>ProcessJob: notifyUser(userId, 'Upload completed')
    end


## System constraints

- Maximum 200 rows per CSV file for batch upload processing
- All-or-nothing validation: if any CSV row fails validation, no expense records are created
- FX rate lookup: maximum 30-day lookback from expense date, return 'No FX Available' if not found
- CSV file size: maximum 10MB (10240 KB) for upload
- Merchant Name maximum length 180 characters per database VARCHAR definition
- Only Primary Administrator has full access to all users' expenses by default
- Administrator requires explicit delegation to manage other users' expenses
- Business User and Card User cannot approve expenses even with management rights
- All queries and mutations must be scoped by client_id for multi-tenancy
- user_id must match authenticated user (server-side validation)
- Target entities (expense_user_id) must belong to the same client_id
- Create ONE Migration per new database table
- Create ONE Eloquent Model per database table using PascalCase naming
- Create ONE Policy per module requiring authorization
- Create ONE FormRequest per API endpoint for validation
- Create ONE Service per domain operation (CRUD, validation, conversion)
- Create ONE API Resource per model returned in responses
- Use InnoDB engine with utf8mb4 character set and utf8mb4_unicode_ci collation
- Apply Laravel SoftDeletes trait for deleted_at timestamp or flag-based soft delete pattern
- All API routes must use OAuth2 middleware for authentication
- Routes should be versioned under /v1 prefix (except /api/uploads/pocket-expense/csv per spec)
- Return proper HTTP status codes: 200/201/204 for success, 400/401/403/404/422 for errors
- Use API Resources to shape responses and hide internal model fields
- Validate request content using Form Request classes with policy enforcement
- Keep controllers thin and delegate business logic to service classes
- Use database transactions for multi-table operations
- Prevent N+1 queries especially in API Resources
- Don't return raw Eloquent models in API responses
- Don't expose stack traces or sensitive error details
- Don't build query filters directly from user input
- Don't forget client_id scoping in all database queries
- Date format for CSV: DD/MM/YYYY (DD-MM-YYYY in template)
- Currency Code must be 3-letter ISO format and validated against platform list
- VAT percentage must be numeric between 0-100 with % sign stripped
- Expense source must match configured sources for client including global 'Other'
- Source Note required when expense source equals 'Other'
- Commission formula: AdjustedRate = BaseRate × (1 - Commission%)
- Backend must recalculate FX on save, do not trust frontend-only values
- Maximum 20 active expense sources per client
- Unique source names per client (client_id, name constraint)
- Global 'Other' record (client_id = NULL) cannot be deleted or edited
- 3 default sources auto-created on feature enable: Cash, Corporate Card, Personal Card
- Date validation: expenses cannot be older than 3 years from current date
- Amount sign determined by expense type: Refund = positive, others = negative
- Header row mandatory in CSV and must exactly match required column names
- Trim notes field and prevent SQL injection, respect database limits
- Use soft delete pattern for expense sources (excluded from dropdowns but visible on historical records)
- Queue job processing: sync expenses in batches of 100 records
- Upload status progression: uploaded → validation_passed/validation_failed → processing → completed/failed
- All expense metadata stored in pocket_expense_metadata with enum metadata_type
- File uploads stored in Laravel storage under pocket-expense-uploads path
- Background job must update upload status and notify user on completion
- Permission delegation can be granted by Primary Admin to any user regardless of role
- Admin can only grant access to their own managed users, not all users
- Managing access enables create/view/edit but approval rights depend on original user role
- Revoked users fall back to Primary Administrator management until reassigned
- Each table with foreign keys must define proper relationships in Eloquent models
- JSON fields (validation_errors, details_json, expense_data) must be cast as array in models
- Timestamp columns follow either Laravel standard (created_at/updated_at) or Volopa legacy (create_time/update_time) per table
- All new tables must include client_id as NOT NULL foreign key for multi-tenant isolation
- UUID fields should be nullable VARCHAR(36) for external reference
- Expense status enum values: draft, submitted, approved, rejected
- File upload status enum values: uploaded, validation_failed, validation_passed, processing, completed, failed, sync_failed
- Staging data status enum values: pending, processing, synced, failed

## Anything UNCLEAR

Three decisions require clarification: (1) Notification channel for batch upload completion - should we implement in-app notifications, email notifications, or both? The system references notifications but doesn't specify the delivery mechanism. (2) The FX conversion integration approach - while the /wallet-ccy-value endpoint exists, the specific implementation of debouncing, commission calculation, and 30-day lookback needs architectural clarity on whether this reuses existing FX infrastructure or requires new service patterns. (3) Table naming convention inconsistency - the specs reference both singular ('client', 'user') and plural ('clients', 'users') table names in foreign key definitions, requiring confirmation of the actual platform convention.
