## Implementation approach

We will implement a Laravel 10+ API system for Volopa OOP Expenses using a modular architecture with three core modules: User Management & Permissions (RBAC with delegation), CSV Batch Upload (sync validation + async processing), and Single Expense CRUD (with FX conversion). The system follows Laravel best practices with thin controllers, service-layer business logic, Form Request validation, API Resources for response shaping, and Eloquent models with explicit relationships. We'll use existing Volopa infrastructure (OAuth2 middleware, queue system, file storage) and integrate with platform tables (users, clients, transaction_category). The architecture supports multi-tenancy via client_id scoping, implements soft delete patterns, and uses background jobs for CSV processing. Key open-source libraries include Laravel's built-in Queue system for async processing, Eloquent ORM for database operations, and Laravel's validation system for comprehensive input validation.

## System constraints

- Maximum 200 rows per CSV file upload
- CSV file format must be CSV or TXT with CSV content
- Maximum file size 10MB (10240 KB) for CSV uploads
- Header row mandatory in CSV and must exactly match required column names
- All-or-nothing validation: if any CSV row fails validation, no expenses are created
- Date must not be older than 3 years from current date
- Date format must be DD/MM/YYYY (DD-MM-YYYY in template)
- Currency Code must be 3-letter ISO format and in platform allowed list
- Amount sign determined by expense type: Refund = positive, others = negative
- VAT % must be numeric between 0-100 (strip % sign)
- Source must match configured sources for client including global Other
- Source Note required when Source = Other
- Merchant Name maximum length per DB definition VARCHAR(180)
- Only Primary Admin has full access to all users by default
- Admin gets full access only to own expenses by default; needs explicit grant for others
- Business User and Card User cannot approve expenses even with management rights
- Managing access can be given to any user irrespective of role
- Admin can only grant access to their own managed users not all users
- Maximum 20 active expense sources per client
- Unique source names per client (client_id, name constraint)
- Global Other record (client_id = NULL) is not deletable or editable
- Soft-deleted sources excluded from future dropdowns but visible on historical records
- 3 default sources auto-created on feature enable: Cash, Corporate Card, Personal Card
- FX rate lookup maximum 30-day lookback from expense date
- If no FX rate found, return No FX Available
- Backend must recalculate FX on save do not trust frontend-only value
- Commission formula: AdjustedRate = BaseRate x (1 - Comm%)
- All queries and mutations must be scoped by client_id for multi-tenancy
- user_id must match authenticated user server-side check
- Target entities expense_user_id must belong to the same client_id
- All new tables must use InnoDB engine with utf8mb4 character set and utf8mb4_unicode_ci collation
- Tables with similar columns across modules are DISTINCT entities with different column types, status enums, and relationships
- When tables track both target user and performing admin, DB column names and API form field names may differ
- Add routes to routes/api.php, usually under /v1 and auth middleware
- Keep route names consistent api.v1.posts.favorite.store pattern
- New tables require migrations and factories
- Add relationships on models with proper foreign key constraints
